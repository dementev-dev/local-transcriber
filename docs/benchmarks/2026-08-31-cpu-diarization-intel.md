# CPU-диаризация: Intel-этап эксперимента

**Дата:** 2026-08-31
**Статус:** `handoff`; в Ryzen-этап передается один кандидат. Production-профиль не менялся.

## Итог

На Intel Core i7-6820HQ пройдены этапы 0-4 эксперимента из
[спецификации](../specs/2026-08-30-cpu-diarization-experiment.md). Для Ryzen
передается комбинация C2:

- `window_shift_ratio=0.1`;
- Pyannote Segmentation 3.0 FP32;
- WeSpeaker ResNet34 LM FP32;
- текущий `FastClustering` с порогом `0.89`;
- два outer worker, одна общая ONNX Runtime session, общий пул из четырех
  intra-op потоков, `inter_op_threads=1`.

C2 сохранила результат baseline по всем обязательным и диагностическим
показателям: `3 / 2 / 2` кластера, та же последовательность слов, те же числа
слов без говорящего `51 / 13 / 9` и та же `mapped speaker purity`. Один прогон
трех фрагментов занял 140,632 с против 146,978 с у соседнего baseline:
ускорение 4,32%. Пиковый RSS вырос с 376,4 до 406,0 МиБ. Порог продолжения на
Intel не достигнут. Разница неотличима от наблюдаемого разброса
одиночных запусков: контрольные baseline в разных сериях лежали в диапазоне
146,978-157,892 с, то есть шире, чем разница между W0 и C2.
Спецификация при этом разрешает передать работоспособный механизм shared-session
как аппаратного кандидата для отдельного A/B на Ryzen. Результат 4,32% остается
диагностическим наблюдением; оценивать по нему ожидаемое ускорение нельзя.

CAMPPlus + NME оказался самым быстрым вариантом: C1 заняла 98,347 с и
сохранила `3 / 2 / 2`. Но на одной записи число слов без говорящего
выросло с 51 до 53. Для такого изменения спецификация требует слуховой проверки
отмеченных мест до сборки комбинации. Материал для нее подготовлен, но в этом
окружении прослушивание недоступно. Поэтому C1 измерена и описана, но в handoff
не включена.

## Зачем понадобился sherpa-onnx 1.13.6

Версия стенда поднята с `1.13.5` до `1.13.6`. В ней публичная Python-конфигурация
сегментации получила `window_shift_ratio`, необходимый для этапа W0-W4. Свежий
контрольный прогон обеих версий дал одинаковые `3 / 2 / 2` кластера, числа слов
без говорящего `51 / 13 / 9` и purity `0,76655 / 0,78742`. Каноническая сверка
интервалов и назначения говорящих словам вынесена в отдельную проверку по сырым
результатам капсулы; расхождений, требующих прослушивания, не обнаружено. Время
одного прогона составило 190,104 с для `1.13.5` и 157,892 с для `1.13.6`; это
диагностическое сравнение без повторов, а не самостоятельное доказательство
ускорения версии.

Экспериментальные `Prepare/Finalize` и общий worker API в `1.13.6` отсутствуют.
Их нет и в проверенном актуальном upstream `master` sherpa-onnx от 2026-08-31.
Для эксперимента собран локальный патч и wheel:

| Артефакт | SHA-256 |
|---|---|
| Патч sherpa-onnx 1.13.6 | `5f12df858cd525c8a0cfe8ff95b647c3b0e915a13d45621acc4ac42660014c49` |
| Wheel CPython 3.13, Linux x86_64 | `306499d8668ee138357f1de43a5c1c88f4dc46c845e8a92e6ad945327bcaa050` |

Проверка патча на реальной модели подтвердила, что worker владеет подготовленным
состоянием. Копирование матрицы и одноразовая финализация работают корректно;
штатный `process()` точно совпадает с цепочкой
`Prepare -> cluster(copy) -> Finalize`. Один и два worker дали одинаковые
строки, метки и итоговые интервалы без пропусков и дублей.

## Условия

- Intel Core i7-6820HQ, 4 физических ядра / 8 логических процессоров;
- 32 181 526 528 байт RAM, x86_64, AVX2; VNNI и AVX-512 отсутствуют;
- Linux 7.0.0-30-generic, Python 3.13.13;
- `sherpa-onnx` 1.13.6, ONNX Runtime 1.28.0, NumPy 2.4.3;
- питание от сети, системный профиль `balanced`, governor `powersave`, turbo
  включен;
- первая попытка финального W0 отбракована из-за swap-in; повторная попытка W0
  и первая попытка C2 прошли runtime guard. В принятых попытках W0 нагрел CPU
  с 80 до 85 C, C2 - с 80 до 82 C; power limits, throttle count и swap I/O
  не изменились;
- три контрольных фрагмента по 300 с, ожидаемые кластеры `3 / 2 / 2`;
- один запуск каждой исследовательской ячейки и одна соседняя пара W0/C2 под
  runtime guard; ASR-sidecar подготовлены заранее и во время ячейки не учитывались.

Измеряемый интервал включает полную диаризацию фрагмента. Для E3 отдельно
помечена составная оценка, потому что независимые session измерялись на заранее
подготовленных заданиях.

## Этап 0: механизмы

`Prepare/Finalize`, общий worker и строгая схема manifest v3 прошли smoke-тесты.
Для CAMPPlus и TitaNet на одних и тех же подготовленных матрицах сравнивались
eigengap и NME:

| TitaNet small | `531 / 414 / 440` | `7 / 2 / 4` | `3 / 2 / 2` | NME |

Ни одна матрица не потеряла строки. Повторный запуск счетчика и штатная

opset и метаданные, прошел ONNX checker, динамические входные длины в ONNX
Runtime и загрузку через sherpa-onnx. SHA-256 графа:
`9a3f8ae64d1083b64a6276f1e1138b17b7511a9a8d731b632945efc84098588b`.

| Ветвь | Время, с | Изменение к W0 | Пиковый RSS, МиБ | Кластеры | Решение |

Время E3 - составная оценка, а не прямое время штатного `process()`. RSS E3 -
максимум всего проверочного процесса: он включает штатную подготовку,
экспериментальные эмбеддинги и контрольную финализацию. Отдельный RSS только
embedding-этапа не измерялся. Даже эта завышенная оценка, включающая соседние
этапы, подтверждает ожидаемый рост памяти с числом session, поэтому E3 не стал
кандидатом.

У E1 и E2 метки, итоговые интервалы и диагностические показатели побайтово
совпали с последовательным вариантом. E1 выбран для C2 как более быстрый и
экономный режим.

TitaNet batch 1 воспроизвел штатные эмбеддинги с максимальным абсолютным
расхождением не больше `3,4e-6`. Batch 4 сохранил `3 / 2 / 2`, но поменял метки
строк на всех трех матрицах, дал дрейф эмбеддингов `0,277-0,317` и оказался
медленнее batch 1. Ветвь остановлена до CPU-ячейки.

## Воспроизведение на Ryzen

После проверки commit и внешнего SHA-256 приватной капсулы:

```bash
uv sync --frozen
uv pip install --python .venv/bin/python --reinstall \
  /path/to/capsule/build/sherpa_onnx-1.13.6-cp313-cp313-linux_x86_64.whl
export LOCAL_TRANSCRIBER_EXPERIMENT_BUILD_SHA256=\
306499d8668ee138357f1de43a5c1c88f4dc46c845e8a92e6ad945327bcaa050
uv run python scripts/benchmarks/diarization_calibration.py \
  --capsule /path/to/original-capsule.zip \
  --capsule-sha256 CAPSULE_SHA256_FROM_HANDOFF \
  --manifest /path/to/capsule/manifest.json \
  --validate-only
```

`--validate-only` должен вернуть schema v3, этап `intel`, пустой список
предупреждений и `qdq_available=true`. Затем Ryzen-агент создает свой manifest
этапа `ryzen`, указывает Intel commit как `handoff_commit` и выполняет
изолированный E1 A/B перед первичным A/B C2. Экспериментальный wheel совместим
только с CPython 3.13 на Linux x86_64; на другой платформе его нужно пересобрать
из патча с тем же SHA-256.

Приватная капсула содержит manifest, исходные записи, ASR-sidecar, опорную
разметку, калибровочные данные, созданные модельные артефакты, сырые результаты,
worker requests и журналы. Эти файлы не входят в Git и не передаются внешним
ревьюерам.

## Ограничения

- У каждой ячейки один прогон. Проценты не оценивают дисперсию, прогрев и
  температурный дрейф.
- Ранние ячейки запускались не чередующимися парами, поэтому полного A/B не
  образуют. Финальные механизмы на Ryzen следует проверять только чередующимися
  парами из спецификации.
- Сравнение sherpa-onnx 1.13.5 и 1.13.6 показывает равенство качества, но разницу
  времени нельзя приписывать одной версии без повторов.
- C1 нельзя возвращать в матрицу без слуховой проверки подготовленных мест.
- Полные записи и приемка пяти слуховых категорий относятся к Ryzen-этапу после
  выбора финалиста.
- Вывод относится к одному Intel Core i7-6820HQ без VNNI/AVX-512. Результаты
  QDQ и shared-session нельзя переносить на Ryzen без собственного A/B.
