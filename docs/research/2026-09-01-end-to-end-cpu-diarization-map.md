# Карта end-to-end архитектур CPU-диаризации

**Дата:** 2026-09-01

**Статус:** выбран один кандидат для свежего минимального A/B - Streaming
Sortformer 4spk v2 Q8_0 через закрепленный NeMo-Speech.cpp. Это единственная
ветвь, где полная замена каскада опирается на готовые Q8_0 веса и закрепляемый
локальный CPU runtime. Production-профиль, CLI, конфигурационный контракт и
модель по умолчанию не меняются.

Документ сохраняет обезличенные агрегаты задач #41 и #42. Старые закрытые
хранилища временно остаются архивом только для чтения до завершения и приемки
задачи #46. Ни стенд, ни сравнение в задаче #46 не должны получать к ним доступ:
новая измерительная основа создается заново. После приемки нового результата
архив можно удалить; тогда его данные нельзя будет получить повторно без нового
вычисления. Здесь нет локальных путей, идентификаторов записей, текста,
временных интервалов, manifest-содержимого или сырых строк результата.
Непрозрачные SHA-256 уже опубликованных результатов оставлены как устойчивые
ссылки на исторические байты. Они не создают будущую зависимость от этих байтов.

## Как читать реестр

`Ускорение` ниже означает сокращение wall time:

`100 x (wall_baseline - wall_candidate) / wall_baseline`.

Отрицательное значение означает замедление. Intel W/M/Q/E - одиночные
разведочные прогоны трех 300-секундных фрагментов, если явно не указана соседняя
пара. Ryzen-строки - принятые соседние A/B. ASR, загрузка моделей и декодирование
не входят в wall.

Обязательный автоматический gate: `3 / 2 / 2` голосовых кластера, неизменный
текст, повторяемые параметры/метки/финализация, конечные эмбеддинги и отсутствие
потерянных или продублированных входов. `51 / 13 / 9` слов без говорящего и
`mapped speaker purity = 0,76655 / 0,78742` - диагностика совпадающего baseline,
а не ручная истина. Рост диагностического показателя требует прослушивания, но
сам по себе не превращает вариант в проигравший.

## Переносимые рецепты

Все Intel-рецепты используют четыре физических ядра; Ryzen-рецепты - восемь.
Везде `inter_op_threads=1`, batch 1, если строка не говорит обратного.
Код измерительного стенда закреплен source commit
`6345cb6449d906767b6ed33e695f2ca4eeaf3008`; sherpa-onnx 1.13.6 - upstream
commit `1cb484af9b1ab05cc36f89e03dd7d76322f2e911` плюс опубликованный ниже патч.
Последовательные W0-рецепты используют CPU provider для segmentation и
embeddings, `debug=True` для обеих конфигураций,
`min_duration_on=0.3` и `min_duration_off=0.5`. Debug-режим входит в
измерительный рецепт: из его журнала получены native stage times.

## Измеренное разложение текущего Ryzen baseline

### Семантика полей

В непатченном последовательном baseline outer `wall_seconds` измеряется вокруг
одного `diarizer.process(samples)`. Native debug отдельно дает
`segmentation_seconds`, `embedding_seconds`, `clustering_seconds` и
`engine_total_seconds`. Поэтому для каждого из трех фрагментов, а затем для их
суммы, допустимо вычислить:

`orchestration = measured outer wall - native engine total`.

Это остаток границы Python/native плюс progress callback и измерительный
обвес; схема не позволяет разложить его дальше и не доказывает, что весь остаток
принадлежит production-коду. Native stage и native total напечатаны с точностью
до `0,001 с`; таблица округляет итоговые суммы до `0,001 с`. Разность использует
сохраненные числа, до отображения не округляется.

У патченного shared-session runner `engine_total_seconds` намеренно записан
равным outer wall всего `Prepare + counter + clustering + Finalize`. Это не
отдельный native total. Поэтому для E1/C2 нельзя честно вычислить orchestration
как `outer - native`: соответствующая величина **недоступна**, а ноль был бы
артефактом схемы.

## Открытые gates и неизмеренные факты

1. **C1 остается неразрешенным слуховым gate - ни победитель, ни проигравший.**
   Обязательная автоматическая проверка прошла, скорость на Intel превысила
   30%, purity выросла, но два
   дополнительных слова без говорящего требуют человеческого прослушивания.
   Автоматические метрики не разрешают этот выбор.
2. Полные записи не измерялись ни для C1, ни для C2. C1 не дошла до Ryzen, C2
   не прошла финальный порог скорости.
3. Ryzen C1 wall/RSS/quality неизвестны полностью; переносить Intel `33,65%` на
   другую ISA нельзя.
4. Для shared-session E1/C2 нет schema-compatible native total и, следовательно,
   нет candidate-side orchestration share. Доступные segmentation/embedding/
   clustering поля не закрывают остаток `counter + Finalize + Python` отдельными
   сопоставимыми стадиями.
5. Orchestration baseline - измеренный residual, но его production/harness
   состав не измерен.
6. Температура Ryzen во время ячеек недоступна. Внешний power/throttle
   guard прошел, но не заменяет сенсор внутри WSL.
7. Intel W/M/Q/E разведка - по одному прогону, ранние ячейки не чередовались;
   их проценты не являются оценкой дисперсии.
8. End-to-end архитектуры не входили в матрицу. Измерены только локальные
   изменения прежнего каскада.
9. `M1` отсутствует по дизайну, C0 пропущена как точный baseline-дубликат,
   stage 6 пропущен по правилу "нет победителя"; это известные пропуски, а не
   потерянные результаты.
10. Отдельные агрегаты Intel companion-ячеек M0/Q0/E0 не опубликованы. Их можно
    использовать только как recipe-alias W0, а не выдавать за новые замеры.

## Что станет невосстановимым после удаления замороженных хранилищ

Удаление обоих хранилищ отложено до завершения и приемки задачи #46. Пока они
сохраняются, их можно использовать только для ретроспективного аудита старых
результатов, но не как вход или базу сравнения нового опыта. После удаления
останутся публичные рецепты, агрегаты, решения и непрозрачные хеши, но сами хеши
уже нельзя будет повторно сверить с исходными байтами.

Без нового model run или повторной подготовки будут потеряны:

- все raw per-recording outer/stage/CPU/RSS значения за пределами опубликованных
  агрегатов, включая точное восьмиклеточное Ryzen-разложение;
- сырые интервалы разметки говорящих, назначения слов, диагностические records,
  ASR-sidecars и опорные материалы;
- prepared embedding-матрицы, row mappings, промежуточные результаты счетчиков,
  worker requests и native logs, которыми проверялись строки/метки/финализация;
- runtime-guard свидетельства и полное состояние планировщика/manifest, включая
  непубличные идентификаторы ячеек и порядок внутренних повторов;
- подготовленные C1 listening excerpts и plan. Пока архив существует, они
  доступны только для отдельного аудита C1 и не входят в задачу #46. После
  удаления для будущего решения C1 придется заново построить минимальный
  baseline/C1 diff и новые excerpts из исходных записей;
- calibration provenance и байты QDQ-графа, локальные wheel/patch artifacts,
  если они отдельно не сохранены; опубликованный SHA доказывает идентичность
  только при наличии байтов;
- возможность расследовать расхождения публичного 1.13.5 hash/wall и W0 RSS по
  исходным файлам.

Исходные записи, по условию задачи #45, останутся лишь удобными входами для нового
минимального среза. Они не восстанавливают старые sidecars, prepared matrices,
слуховой plan, environment state или старые timing samples без повторного
вычисления.

Исторические строки выше описывают прежний каскад и прежние контрольные
фрагменты. Они отвечают на вопрос, какие локальные изменения уже проверены.

## Класс архитектур и формула полной замены

Текущий путь строит разметку говорящих каскадом `segmentation -> embeddings ->
clustering`. В sherpa-onnx 1.13.6 отдельный эмбеддинг вычисляется для каждой
пары локального говорящего и окна; это подтверждает
[upstream-реализация](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.6/sherpa-onnx/csrc/offline-speaker-diarization-pyannote-impl.h).
Суммарное разложение выше показывает, что локальные изменения embeddings имеют
большой доступный бюджет, однако принятый 30%-й результат на Ryzen не получен.

Для сравнения архитектур используется одна формула:

```text
B = S + E + C + O
T_candidate = B - R + A
speedup = (R - A) / B
идеальный предел при A = 0: R / B
```

`B` - measured outer wall текущего W0; `S`, `E` и `C` - измеренные native
стадии; `O` - derived residual `outer wall - native engine total`; `R` - работа
старого пути, которую удаляет гипотеза; `A` - измеряемая работа новой
архитектуры. Для полной замены `R = B`, поэтому фактическое сокращение равно
`1 - A / B`. Upstream не публикует переносимый CPU RTF для выбранной модели;
числовой прогноз `A` отсутствует. Его определит свежий A/B.

## Реестр архитектурных гипотез

### A1. Streaming Sortformer v2 Q8_0 через NeMo-Speech.cpp - выбран

**Механизм и затронутые стадии.** NEST/Fast-Conformer encoder и следующий за
ним Transformer выдают четыре sigmoid-потока активности. Arrival-Order Speaker
Cache связывает говорящих между streaming-чанками; порядок меток задается
первым появлением голоса. Модель возвращает `T x 4` вероятностей с шагом 80 мс
и заменяет текущие segmentation, embeddings, подсчет/кластеризацию и
финализацию. Архитектура описана в
[карточке модели NVIDIA](https://huggingface.co/nvidia/diar_streaming_sortformer_4spk-v2)
и [первичной статье](https://arxiv.org/abs/2507.18446).

**Поведение quality gate.** Потери W1-W4 возникли после прореживания
10-секундных окон перед независимыми эмбеддингами. Sortformer оценивает
перекрывающиеся активности общей сетью и не использует эту сетку или порог AHC.
Ошибки могут перейти в границы 80-мс кадров, рождение канала и сохранение метки
в speaker cache, поэтому точное число кластеров и слуховая проверка остаются
обязательными.

**Предел и риск.** Полная замена дает идеальный предел 100% вызова, а
фактическое сокращение `1 - A_sortformer / B`. Опубликованный RTF `0,002`
измерен на RTX 6000 Ada, batch 1, и не является CPU-прогнозом
([model card](https://huggingface.co/nvidia/diar_streaming_sortformer_4spk-v2#setting-up-streaming-configuration)).
Модель имеет четыре выходных канала говорящих; NVIDIA предупреждает о
деградации на пяти и более слышимых голосах, неанглийской речи, другом домене и
очень длинных записях
([technical limitations](https://huggingface.co/nvidia/diar_streaming_sortformer_4spk-v2#technical-limitations)).

**Самая дешевая фальсификация.** На Ryzen выполнить один свежий W0 и одну
соседнюю пару W0/Sortformer на трех заново определенных пятиминутных
фрагментах. Остановить ветвь при несовпадении с новыми ожидаемыми числами
кластеров, нарушении текстовой инвариантности, OOM/swap/росте RSS без плато или
ускорении меньше 10%. Точный контракт находится в
[спецификации следующего эксперимента](../specs/2026-09-01-streaming-sortformer-cpu-experiment.md).

**Повторное использование.** Переносятся рецепт Ryzen W0, правила gate,
каноническое сведение `Word` с `SpeakerInterval`, безопасные агрегаты и
сохраненные исходные записи. Sidecar, опорная разметка, фрагменты и закрытое
хранилище создаются заново. Prepared matrices, старые интервалы, патч и wheel
не используются.

**Исполнимость.** NVIDIA публикует готовый Q8_0 GGUF, нативный Apache-2.0
runtime с CPU backend и отдельным API диаризации
([NeMo-Speech.cpp](https://github.com/NVIDIA/NeMo-Speech.cpp),
[C ABI](https://github.com/NVIDIA/NeMo-Speech.cpp/blob/4f9676226f667d14608487df744f375db87127f8/include/nemo_speech/diar.h)).
Веса имеют CC BY 4.0. Runtime и модель закреплены в следующей спецификации.
Выбор разрешает только изолированный исследовательский стенд.

может изменить решение. Второй кандидат в короткий список не добавлен, потому
что для него сначала пришлось бы создавать runtime или выбирать новые веса.

## Решение и владение соседними задачами

Следующее измерение проверяет ровно A1. Причины выбора: полная замена старого
вызова, готовые Q8_0 веса, закрепляемый нативный CPU runtime и standalone
разметка говорящих без изменения ASR. Контракт исполняет
[задача #46](https://git.dementev.space/ddmitry/local-transcriber/issues/46).
В задаче #45 модель и аудио не запускались.

Параллельное планирование ASR и диаризации целиком принадлежит
[задаче #22](https://git.dementev.space/ddmitry/local-transcriber/issues/22).
Автоматическое включение принадлежит
[задаче #23](https://git.dementev.space/ddmitry/local-transcriber/issues/23).
Joint ASR+diarization и shared-ASR-encoder меняют путь распознавания и исключены
из этой карты. ASR-sidecar используется только как свежий quality input.

Принятие A1 после эксперимента означает право подготовить отдельное
production-решение. Оно не меняет [ADR-007](../adr/007-word-level-speaker-diarization.md)
и не разрешает поставку NeMo-Speech.cpp в основном dependency graph.
